# Deploying Giftlio

This is the real, complete deployment guide for this project — every environment
variable actually used in the code, in what order things need to happen, and
what to check before calling a deployment "live."

## 1. Accounts you need

- **Vercel** — hosting, both the static site and the `api/` serverless functions
- **Supabase** — database, auth, storage, and realtime
- **Stripe** — payment processing
- **Resend** — transactional email

## 2. Environment variables

Set these in **Vercel → Project Settings → Environment Variables**, for both
Production and Preview. Nothing below is guessed — this list was generated by
grepping every `process.env.*` reference actually used in the codebase.

| Variable | Required? | Where to get it | Used by |
|---|---|---|---|
| `SUPABASE_URL` | Yes | Supabase → Project Settings → API → Project URL | Build step (client config) + all `api/` functions |
| `SUPABASE_ANON_KEY` | Yes | Supabase → Project Settings → API → `anon` `public` key | Build step (client config) |
| `SUPABASE_SERVICE_ROLE_KEY` | Yes | Supabase → Project Settings → API → `service_role` key | All `api/` functions (server-side only — never expose this client-side) |
| `STRIPE_SECRET_KEY` | Yes | Stripe → Developers → API keys | `create-checkout.js`, `webhook.js` |
| `STRIPE_WEBHOOK_SECRET` | Yes | Stripe → Developers → Webhooks → your endpoint → Signing secret | `webhook.js` — **without this, the webhook's signature check fails closed and no orders will ever complete**, this isn't optional |
| `RESEND_API_KEY` | Yes | Resend → API Keys | Every function that sends email |
| `EMAIL_FROM` | No — falls back to `Giftlio <onboarding@resend.dev>` | Set once you've verified a domain (see section 5) | Every function that sends email |
| `ADMIN_NOTIFY_EMAIL` | No — falls back to `giftlio.co.nz@gmail.com` | Your own inbox | `send-notification.js`, `webhook.js` |
| `CONTACT_FORM_TO` | No — falls back to `support@giftlio.co.nz` | Wherever contact form submissions should land | `contact-form.js` |

`NEXT_PUBLIC_SUPABASE_URL` also works as an alternate name for `SUPABASE_URL` (some of the functions check both) — you only need to set one of the two.

## 3. Supabase setup

1. Create a Supabase project.
2. Run every file in `supabase/migrations/` **in filename order** (they're timestamped, so sorting alphabetically is sorting chronologically). Either paste each one into the SQL Editor, or use the Supabase CLI if you have it.
3. Confirm the `receipts` storage bucket exists (created by the `20260803000000_receipt_storage.sql` migration) — Supabase → Storage, should show as **private**, 5MB limit, JPG/PNG/PDF only.
4. Confirm Realtime is enabled on `brand_discounts` (from `20260801030000_enable_brand_discounts_realtime.sql`) — Supabase → Database → Replication, `brand_discounts` should be listed.
5. Manually promote your own account to admin after you sign up through the app once: `update public.profiles set role = 'admin' where email = 'your-email@example.com';`

## 4. Stripe setup

1. Get your API keys from Stripe → Developers → API keys. Use **test mode** keys until you're genuinely ready to take real payments.
2. Create a webhook endpoint pointing at `https://your-domain.vercel.app/api/webhook`, subscribed to at least `checkout.session.completed`.
3. Copy the webhook's signing secret into `STRIPE_WEBHOOK_SECRET`.
4. **Test mode vs live mode uses entirely separate API keys and webhook secrets.** Switching to live mode later means updating all three Stripe-related env vars, not just flipping a toggle.

## 5. Resend setup — read this before you assume email is working

Out of the box, with no domain verified, Resend only allows sending to **your own account email**. This project already falls back gracefully to Resend's test sender (`onboarding@resend.dev`), so nothing will throw an error — but every email meant for an actual seller or buyer will silently fail and land in `email_queue` with `status: 'failed'` (visible in Admin → Email Notifications).

**Before launch:**
1. Verify a domain at resend.com/domains.
2. Set `EMAIL_FROM` to an address on that domain, e.g. `Giftlio <noreply@giftlio.co.nz>`.
3. Redeploy.
4. Confirm with a real test (see checklist below) — check that a real, non-owner email address actually receives something.

## 6. Vercel deployment

1. Connect the GitHub repo to a new Vercel project.
2. Set every environment variable from section 2.
3. Deploy. The build runs `npm run build`, which runs `scripts/generate-env.js` — this writes `env-config.js` at build time from `SUPABASE_URL`/`SUPABASE_ANON_KEY`. If those two aren't set, the build fails on purpose rather than deploying a broken site.
4. Confirm the deployment is green in Vercel's dashboard.

## 7. Before calling it live — a real checklist, not a guess

Run through this yourself, with two real accounts (a seller and a buyer), before telling anyone this site is open:

- [ ] Sign up as a seller, submit a real (or test) gift card with a receipt image attached
- [ ] Confirm the seller receives a real "submission received" email — not just a toast in the browser
- [ ] Log in as admin, confirm the submission shows up with the receipt viewable, approve it
- [ ] Confirm the seller receives a real "approved" email with the payout amount
- [ ] Confirm the card now appears in Browse
- [ ] Buy it with a second (buyer) account, using a real Stripe test card
- [ ] Confirm the buyer receives a real order confirmation / delivery email
- [ ] Confirm the order shows up correctly in Admin → Active Listings as sold, and in the buyer's Order History
- [ ] Check Admin → Email Notifications — if anything shows `failed`, don't launch until you know why (almost certainly the Resend domain issue in section 5). Failed rows can be resent from here: a per-row "Retry" button retries just that email, "Retry All Failed" retries every failed row (up to 5 attempts each) — both call `api/retry-failed-emails.js`. There's no scheduled retry job wired up yet, so a failed email stays failed until someone clicks one of these.
- [ ] Check Admin → Audit Log — confirm the approval action you just took is actually logged

If every one of those is true with real emails landing in real inboxes, the core loop works end-to-end. If you skip this and only check that the code runs without errors, you won't catch the difference between "the function returned 200" and "the seller actually got an email."

## 8. Known gaps to revisit before real launch

These aren't blockers for testing, but are real and worth tracking:

- **CORS is hardcoded** to `https://card-swap-nz.vercel.app` in `vercel.json`. If you add a custom domain, that line needs updating or your own API calls will start getting blocked by the browser.
- **Card numbers and PINs are encrypted at rest** (`20260803020000_encrypt_card_data_at_rest.sql` — `BEFORE INSERT` triggers on `submissions` and `card_vault`, key in Supabase Vault, `decrypt_card_value()` gated to admin sessions and the service role). Pre-migration test rows were retroactively encrypted (or deleted, where genuinely unused) in `20260817120000_encrypt_legacy_plaintext_card_data.sql`. Nothing plaintext remains in either table as of that migration.
- **Legal footing on reselling gift cards** is genuinely a gray area — most retailers' own terms restrict resale of their cards. Worth 30 minutes with an NZ small-business lawyer before real money moves at volume, not after.
- **Resend domain verification** (section 5) — until this is done, no seller or buyer has ever received a real email from this platform, regardless of how correct the code is.
